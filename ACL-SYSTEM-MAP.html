01 Architecture

A Laravel modular monolith. Every request enters through one of three gated paths, passes down through controllers and services, and lands in a single TiDB cluster. ACLi is the only outbound dependency.

The central weakness. buildProviderMessages() sends a fixed, generic system prompt: "You are ACLi, an educational AI assistant for ACL." Meanwhile CurriculumContextService — which already resolves programme, curriculum version, level, semester and the student's actual course codes — is fully written and never called by anything. ACLi is currently a generic chatbot wearing a student-facing interface. It cannot answer "what am I taking this semester" because it is never told.
And a containment gap: studentChat() verifies a user exists and holds the capability, but never verifies that user is a student. A staff account granted acli.student.chat reaches the student capability.

Scope resolves into the wrong table. A role assignment is scoped with entity_type = Organization::class, entity_id → organizations.id. But the institutions list, student records and course scoping all key off Institution / institutions. The live staff invitation carries organization_id = 2000001 — which resolves in organizations and is NULL in institutions. Staff are scoped against a table the rest of the academic model does not use. This is the single most consequential structural problem in the app.
Duplicate role name. "Institution Admin" exists twice with different slugs, so role lookups by name are ambiguous and one branch is unreachable through name-based selection.

Coverage is the real product risk. 542 users but 11 student records; 5 placed against an institution; 0 course registrations; 1 offering and 1 lesson for the whole platform. Consequence. The two ID spaces do not overlap. The one live staff invitation points at organization_id = 2000001 — present in organizations, NULL in institutions. 08 Issue Register

Every open item, ordered by consequence. All verified against production, not inferred from source.

P0No rate limiting anywhere in the application
Zero throttle middleware on any of the 78 routes and zero RateLimiter::for() definitions. Login is brute-forceable; JAMB verification is unmetered against a paid external API; ACLi chat is unmetered so one entitled student can drain the gateway.
verified: grep throttle bootstrap/app.php app/Providers routes/*.php → 0 hits grep RateLimiter::for app/ bootstrap/ → 0 hits middleware on login / acli.chat.send / register.student.verify → web|guest, web|auth, web|guest
P0Institution / Organization data fork — two ID spaces
institutions (474) and organizations (126) both model an institution. 26 call sites use Organization, 7 use Institution. The live staff invitation's organization_id is NULL in the other table. Scope isolation currently resolves against a table the academic model does not use.
institutions=474 organizations=126 invitation.organization_id=2000001 → Organization: "Northwest University, Kano" · Institution: NULL Organization:: refs=26 Institution:: refs=7
P0ACLi does not verify the caller is a student
studentChat() checks that a user exists and holds the student.chat capability, but never checks $user->student exists. A staff or admin account granted the capability reaches the student AI capability.
AcliOrchestrator.php:41-47 → Auth::user() check only reflection scan of studentChat source for ->student → no match
P168 of 116 migrations are missing from the repository
Only 50 migration files exist. The missing 68 include the entire curriculum chain — programmes, courses, curriculum_courses, course_outlines, assessments — plus the identity and admin tables. The repository cannot rebuild the database, and this is the direct cause of every failing test suite.
